# R130-09 YouTube 發送與持久化

沿用 `social-worker`、既有 scheduler key 和 R130-08 範本。YouTube 發送分支限 Staging `eziafqttckcdvjxxvxsv`，並要求 `YOUTUBE_SEND_ENABLED=true` 以及頻道資料列 `r130_youtube_settings.send_enabled=true`。兩個開關預設關閉。此次交付只包含程式、遷移及測試。Production 維持 NO_GO。

## V38 後續調整

- YouTube 預覽以 GET 讀取已儲存的頻道基準。尚無資料列時使用有效的 `YOUTUBE_REPLY_BASELINE_AT`，未設定時使用當次請求開始時間。預覽仍為每次 YouTube Data API 讀取更新資料庫額度。
- 單次執行沿用既有頻道與全域發送閘門。送出前重新確認環境發送開關、單次測試留言 ID 與 Staging 來源。Production 維持 NO_GO。

## R130-09 留言基準與額度

- 首次預覽或執行會儲存頻道基準，使用 `YOUTUBE_REPLY_BASELINE_AT` 或資料庫當下時間。後續請求讀取原基準。首次執行前可提供已確認的歷史截止時間。
- 每則留言以頻道 ID 和留言 ID 唯一認領。認領、額度占用及發送開關檢查在同一筆 PostgreSQL 交易內完成。跨 Worker 共用每日 150 次發送嘗試，失敗或結果未知的嘗試也保留額度。
- 所有 YouTube Data API 讀取及發送共用每日 10,000 單位。讀取 1 單位，`comments.insert` 50 單位。讀取重試也扣額度，Google 回報每日配額耗盡會封鎖當日讀寫。資料庫以 `America/Los_Angeles` 換日。發送會避開換日前 20 秒。
- 預覽會寫入基準及額度紀錄，YouTube 端只有讀取。每次掃描最多五頁，超出時回傳 `partial`。掃描範圍內每輪最多處理十則尚未認領的候選，優先處理較早的留言。長時間停機或大量留言造成連續 `partial` 時，需要人工檢查較早的留言。

## 發送確認與恢復

- 發送前使用 `comments.list` 查詢既有回覆。認領成功後呼叫一次 `comments.insert`，使用成功回傳的回覆 ID 結案。
- 逾時、連線錯誤、無法辨識的成功回應或伺服器錯誤均視為結果未知。先查詢回覆，核對頻道、原文和發送時間。若無法確認，保留認領供後續查證。
- Worker 中斷時，後續執行可領取過期的 `sending` 或 `uncertain` 查證工作，每輪最多五筆。沒有查證到回覆的認領維持待查，明確拒絕則保留拒絕紀錄。這兩種結果均需人工決定後續處置。
